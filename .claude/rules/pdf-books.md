# PDF & Companion Books

Path-gated out of `distributed-narrative.md` (2026-10-16, ADR-111 amendment): build, render, layout, QR and KDP rules for the DN-S PDF chapter-books and companion formats. The always-on pointer lives in `rule-index.md`. Each section keeps its original heading.

## The dual-tier PDF chapter-book has a self-checking COVERAGE + FRESHNESS guard — a chaptered app with no book, or a book rendered before its multi-beat illustrations, is never silently forgotten (R-PDF-BOOK-COVERAGE; 2026-07-28)

**The dual-tier DN-S PDF chapter-book has a self-checking COVERAGE + FRESHNESS guard (`scripts/check_pdf_book_coverage.py` + `Docs/REGISTRY_PDF_BOOK_COVERAGE.txt`, SHAPE-B WARN — the surfaces degrade gracefully) so a chaptered app with no book, or a book rendered before its multi-beat illustrations, is never silently forgotten. The render pipeline is MANUAL + was dormant, so both gaps grow invisibly. Guards read ORIGIN, not the (routinely-behind) shared site clone (§ R-CANONICAL-DOC-GROUND-TRUTH).**

→ **Full detail:** `Docs/REFERENCE_DISTRIBUTED_NARRATIVE.md` § (this heading) — the two failure modes + the reconciler recipe + the reference reconciliation (162/163 fresh).
## PDF chapter-books order their chapters in PEDAGOGICAL (curricular-arc) order — the `dnCast.members[]` index, NEVER alphabetical (R-PDF-BOOK-PEDAGOGICAL-ORDER; 2026-07-28)

**A dual-tier DN-S PDF chapter-book MUST present its chapters in the app's CURRICULAR / PEDAGOGICAL progression — the order the app introduces each primitive — which IS the `apps.generated.ts` `dnCast.members[]` arc index (R-DN-CAST-ORDER), NOT alphabetical-by-filename. A book whose TOC is an alphabetical jumble (e.g. Dot · Equi · Gather · Halver · Liner · Pie · Rank) instead of the learning path (Halver → Pie → Equi → … → Rank) is a defect.** Codified per founder-direct 2026-07-28 (*"the multi-beat chapters in the pdf books should follow pedagogical order"*), after the V635 render surfaced the alphabetical default. This is the PDF-book sibling of `spark-anvil-website.md` § R-WEB-CLONE-PEDAGOGICAL-ORDER (the `/play` clone-index sort) + § R-DN-CAST-ORDER (cast/story lists) — same principle (browse/read ORDER is a pedagogical signal), same source-of-truth (`dnCast.members[]`).
## The dual-tier PDF chapter-book MUST be functional · intuitive · engaging · prominent — a Stage-1 UX standard, enforced in the build + verified by a sample VISUAL audit (R-PDF-BOOK-UX; 2026-07-28)

**Every DN-S PDF chapter-book (Standard/Blubook + Advanced/Folio) MUST meet the FUNCTIONAL · INTUITIVE · ENGAGING · PROMINENT UX standard below, enforced DETERMINISTICALLY in the Stage-1 build (`build_pdf_book_per_app.py`) — and a book's UX quality is confirmed the way `/play` UI is: a SAMPLE VISUAL AUDIT (read the actual rendered PDF pages), not the build log. A book that ships with a raw-markdown leak, a cluttered/double-entry TOC, an empty/thin chapter set, a reader-facing register leak, or alphabetical-not-pedagogical order is a UX defect on the same footing as a `/play` clone that "builds green but looks wrong."** Codified per founder-direct 2026-07-28 (*"make the pdf books functional, intuitive and engaging and prominent. deep web research and think harder … codify these too."*); research `RESEARCH_PDF_BOOK_UX_2026-07-28.md` (foreground-sequential, cited); audit + shipped fixes `AUDIT_PDF_BOOK_UX_2026-07-28.md`. This is the UX sibling of § R-PDF-BOOK-COVERAGE (does the book exist + is it fresh?) + § R-PDF-BOOK-PEDAGOGICAL-ORDER (are the chapters in arc order?) — this rule governs whether the book, once it exists, is GOOD.
## Every book renders at an AGE-BAND-CALIBRATED base font size — bigger for younger readers; the raw Blubook 14px / Folio 17px is TOO SMALL (below every children's-book typography floor); Typora export is controlled via injected document CSS, NOT the on-screen preference (R-PDF-BOOK-FONT-SIZE; 2026-08-03)

**Every companion book — the illustrated STORYBOOK and every companion format (activity · coloring · puzzle · volume · flashcard · jokebook) — MUST render its body text at an AGE-BAND-CALIBRATED base font size that is BIGGER for younger readers, because the raw Typora themes are objectively too small: Blubook (tier-1 / 9-14 Standard, which ALSO renders the younger 3-5/6-8 illustrated storybooks) has `html { font-size: 14px }` ≈ 10.5pt, and Folio (tier-2 / 11-14 Advanced) has `17px` ≈ 12.75pt — BOTH below the children's-book typography floors (chapter/middle-grade ~12-14pt; early-reader/picture-book 14-24pt, +4-6pt leading), and the same ~10.5pt was rendering the YOUNGER storybooks that should be 16-24pt (the exact "font size for younger storybooks is very small" the founder flagged 2026-08-03). A book rendered at the raw theme baseline — especially a younger-band storybook — is a legibility/age-appropriateness defect on the same footing as a failed R-PDF-BOOK-UX axis.** Codified per founder-direct 2026-08-03 (*"font size for the younger storybooks is very small … font sizes for all age bands should be bigger … can we control font sizes when exporting via Typora? deep web research, audit, verify, track, codify"*); evidence `RESEARCH_PDF_BOOK_FONT_SIZE_2026-08-03.md`. This is the type-SIZE authority under § R-PDF-BOOK-UX (which governs white-space/hierarchy but never fixed the base size).
## A multi-beat book's beat prose is CLAMPED past the leading YAML front-matter — a stale sidecar `prose-range` that lands inside the (later-grown) front-matter leaks raw keys (`reflection-prompts:` / `prompt:` / `gate-allow-text*:`) verbatim into the rendered book; the automated build is BLIND to it, only the pixels / pdftotext catch it (R-PDF-BOOK-FRONTMATTER-LEAK; 2026-08-05)

**The multi-beat PDF-book builder (`build_pdf_book_per_app.py` `_build_multibeat_body`) slices each beat's prose from the snapshot MD by the sidecar's `prose-range: {from-line, to-line}` line coordinates. Those coords index against the snapshot's LINE NUMBERS, but a chapter's YAML front-matter routinely GROWS after the sidecar was segmented (the R-DIR-FEDC-CHAPTER `reflection-prompts:` block, `gate-allow-text:`/`gate-allow-text-pattern:` gate fields, added by later authoring passes) — so a stale beat `from-line` points INSIDE the front-matter, and the raw YAML keys render VERBATIM in the kid-facing book body. Every beat's `from-line` MUST therefore be CLAMPED past the leading `---...---` front-matter block (no prose can live inside front-matter, so the clamp only ever drops leaked YAML). A builder that slices a beat without the front-matter clamp is a text-leak defect on the same footing as a failed dark-mode axis.** Codified per founder-flag 2026-08-05 (*"I just saw the words 'prompt' in the pdf books. are they text leaks? do a full audit … and regen if needed"*); the founder-spotted `prompt:` was exactly this leak.
## The PDF chapter-book GENERATION process is ONE canonical 8-stage pipeline — follow `GUIDE_PDF_BOOK_GEN_PROCESS.md`; NEVER improvise the order (R-PDF-BOOK-GEN-PROCESS; 2026-07-29)

**Producing a portfolio app's dual-tier illustrated PDF chapter-book (Standard/Blubook 9-12 + Advanced/Folio 11-14) follows ONE canonical, ordered pipeline — the runbook `Docs/GUIDE_PDF_BOOK_GEN_PROCESS.md` — and its stage ORDER is load-bearing; do NOT hand-improvise the steps. Load-bearing invariants: `/usr/bin/python3` for gen/R2 (boto3+google.genai), homebrew `python3` for build/guard; single-flight the Gemini key + R2 mutation; verify against R2 ground truth before paid gen (§ R-GEN-DRAIN-VERIFY-R2-GROUND-TRUTH); covers gate COVERAGE, R2-recency gates FRESHNESS; mandatory sampled VISUAL review of every cover + rendered pages (the print analog of the screenshot-DoD). The Typora GUI render is FOREGROUND-only (foreground Bash `timeout`, ~20 books/batch), needs the Accessibility TCC grant + Typora frontmost (restart Typora first if frontmost-blocked), `shutil.move` cross-device, and a re-run of intermittent focus-steal fails on a clean Typora.**

## The at-cost Amazon-KDP paperback path is a DECIDED-BUT-NOT-EXECUTED, FOUNDER-ACCOUNT-MANAGED distribution channel — hub produces the print-grade artifacts, the founder submits; free PDF stays the primary channel (R-PDF-BOOK-KDP; 2026-07-30)

**The portfolio's PDF chapter-books MAY additionally be offered as at-cost 6×9 paperbacks via Amazon KDP (ADR-023, 2026-06-02: free PDF download from the site + at-cost $5–7 KDP paperback, 501(c)(3)-aligned, phased Wave 1 free-PDF → Wave 2 KDP flagship-5 → Wave 3 portfolio-KDP-gated-on-Wave-2-signal). As of 2026-07-30 ONLY Wave 1 (free PDF) has EVER shipped — the KDP paperback path was DECIDED but NEVER EXECUTED (no `kdp_post_process.sh`, no KDP-grade PDFs, no ISBN, no Amazon listing, no `/books` buy-link), and it had DECAYED out of the standing rule set (0 mentions) until this codification. The KDP channel is ENTIRELY FOUNDER-ACCOUNT-MANAGED — like the Cloudflare backend work, hub CANNOT execute it (KDP submission is a MANUAL, per-book, no-programmatic-API action on the founder's Amazon account, plus ISBN + pricing choices). So the ownership split is HARD: HUB produces the print-grade artifacts (a 6×9/bleed/300-DPI/embedded-fonts/flattened print PDF + a KDP-grade cover); the FOUNDER submits/lists/prices on KDP. The FREE PDF download stays the PRIMARY, always-on channel — KDP is a supplementary at-cost convenience, never a paywall in front of the free books.**
## Every companion book embeds QR codes → the audio drama + website deep links (printed with a text URL, plain no-tracking links) — a book that bridges back to the site, and a QR-less book is a tracked backlog item, never silently forgotten (R-PDF-BOOK-QR-LINKS; 2026-08-01)

**Every companion book — the illustrated STORYBOOK and every companion format (activity · coloring · puzzle · volume) — MUST embed QR codes bridging the printed page back to the website: (a) an AUDIO-DRAMA QR to the WEB audio-player page `/cast/<app>/<char>` (NEVER a raw `.m4a` URL), and (b) WEBSITE DEEP-LINK QR(s) in front/back matter to `/play/<app>` + `/cast`-or-`/story` + `/books`. Invariants: QR → a REAL live route (a QR to a 404 is worse than none); PLAIN `spark-and-anvil.org` links, NO tracking param/shortener (COPPA on-device posture); the human-readable short URL PRINTED beside every QR (a bare QR is inaccessible); QRs computed at Typora render time (deterministic, no paid gen) via `scripts/lib/book_qr.py` (config `site_origin()` = `.org`, `has_clone()`/`has_cast()` fail-closed so a book never QRs to a dark route). GATED on the PERMANENT canonical host (a printed QR is IMMUTABLE) — `.org` (V737); the CDN subdomain stays `cdn.spark-and-anvil.com` (infra, never in an immutable artifact). A shipped/re-rendered book WITHOUT QRs (once the builder exists) is a defect; the shipped fleet is TRACKED by `check_book_qr_coverage.py` → `Docs/REGISTRY_BOOK_QR_COVERAGE.txt` (SHAPE-B WARN, QR_EPOCH 2026-08-01; ~97% QR-OK by construction — residual = paid coloring re-gen + crowntales puzzle).**
