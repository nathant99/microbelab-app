# Site Deploy, CI & Prod Ops

Path-gated out of `workflow.md` (2026-10-16, ADR-111 amendment): these rules cover `spark-anvil-site` deploys, the release train, Cloudflare builds, CI cost, prod monitoring and npm dependencies. Their always-on one-liners live in `rule-index.md`. Each section keeps its original heading, so `§ R-…` cross-references still resolve.

## A NEW npm dependency is VETTED onto a human allowlist before it lands — slopsquatting weaponizes AI package hallucinations, so an un-allowlisted / typosquat / hallucinated dep is a supply-chain defect, not a convenience (R-DEPENDENCY-SUPPLY-CHAIN; 2026-08-23)

**Every npm dependency in a surface WE own (`spark-anvil-site` + its Cloudflare Workers) is human-reviewed onto `Docs/REGISTRY_SITE_DEPENDENCY_ALLOWLIST.txt` (name · pin · license · why) BEFORE it lands, a committed lockfile is required (`npm ci`, never bare `npm install`), and a NEW / un-allowlisted dep is a FLAG requiring vetting — existence + registration-age + typosquat edit-distance to popular+allowlisted names + license — because SLOPSQUATTING weaponizes AI package hallucinations (an LLM invents a plausible-but-nonexistent name → an attacker pre-registers it → the next agent installs malware at `postinstall` in CI with our creds; ~20% of AI-suggested imports don't exist, 58% recur, >440K catalogued traps; registry/advisory-DB defenses can't catch a name that was never real → the defense lives in the pipeline). An un-allowlisted, typosquat, or hallucinated dep, or a missing lockfile, is a supply-chain defect on the dark-route footing. Guard: `scripts/check_dependency_supply_chain.py` (SHAPE-B WARN; `--ci-mode` fails on a NEW un-allowlisted dep or missing lockfile; `--online` probes the registry for existence/age). Update the allowlist IN THE SAME PR that adds a dep — that IS the control. The hub is zero-dep Python; app repos are Swift/SPM (`R-FORGEKIT-PIN-CONSISTENCY`). This is the DEPENDENCY/supply-chain front that `R-AGENT-SECURITY-POSTURE` (the agent-as-injectable-process front) did not reach.** Founder-direct 2026-08-23; decision `ADR-184`; evidence `RESEARCH_SE_BEST_PRACTICES_2026_DELTA_2026-08-23.md` §1. Deferred (founder-gated hardening): a live registry-proxy / online existence-probe in site CI + SBOM/Sigstore.

→ **Full detail:** `Docs/ADR-184_SE_BEST_PRACTICES_2026_DELTA.md` + `Docs/AUDIT_HUB_SE_BEST_PRACTICES_2026_DELTA_2026-08-23.md`.
## After merging a play-affecting site PR, WATCH the deploy to completion + ground-truth the LIVE asset — a MERGED PR + green `build:play` does NOT prove LIVE (R-CLOUDFLARE-WATCHED-MERGE-DEPLOY; 2026-08-12)

**After merging a `/play`-affecting `spark-anvil-site` PR, an agent MUST WATCH the deploy to completion and GROUND-TRUTH the LIVE asset before recording SHIPPED — because Cloudflare Workers Builds deploys PLAY-unit builds OUT OF ORDER (§ `spark-anvil-website.md` R-SITE-BUILD-OUT-OF-ORDER), so a MERGED PR + green local `build:play` does NOT prove the change is live. The mechanism (CF `deployments`-API poll for a new `created_on` post-merge + browser-UA `curl` of the live `/play/<clone>/<route>/` grepping the shipped `play.<hash>.css` selector → RE-TRIGGER on a miss) → the turnkey tool below / REFERENCE. Recording SHIPPED on the merge alone (no live-asset grep) is a false-SHIPPED defect on the § R-AUTOMERGE-NOT-MERGED footing.** DETECT+RECOVER half (preventive half = batch/space play merges, § R-BATCH-DISTRIBUTION-PUSH + § R-COMBINE-RELATED-WORK-ONE-PR); tracked `q-84a11f`.

→ **Full detail:** `Docs/REFERENCE_WORKFLOW.md` § R-CLOUDFLARE-WATCHED-MERGE-DEPLOY — the deployments-API poll recipe, the browser-UA curl-grep oracle, the re-trigger method, and the cross-refs.

## Landing a prod FIX = a 5-step FORCE-PROMOTE loop, and a "build green + promoted" is NOT live — a CACHE-RESTORED build serves STALE output; VERIFY THE CONTENT, then cache-bust (R-SITE-FORCE-PROMOTE-AND-VERIFY; founder-direct 2026-08-23, "codify this")

**To force a `spark-anvil-site` prod fix live (and to AUTO-CYCLE prod fixes), run the full loop — a build success is necessary-but-FAR-from-sufficient; the ONLY proof is the live CONTENT:**
1. **PR → `staging`** (ADR-154; auto-cycle branch→commit→PR→merge, base=staging).
1.5. **🔴 PRE-TRAIN FLEET-INVARIANT TRIPWIRE — run BEFORE step 2:** `python3 scripts/check_clone_fleet_invariants.py --ci-mode` (~1s). The train preflight is FAIL-CLOSED on the full fleet Vitest+e2e (level · nav-cap · SEL crisis-footer/988), so a sibling's green-locally regression reds it and blocks the promote only after a ~20-30 min doomed build — catch it in 1s. A flag NOT from your diff = an orthogonal sibling blocker (§ R-CLONE-FLEET-INVARIANT-BEFORE-MERGE): fix or flag+own-lane first, never force past a red fleet gate.
2. **Force the train:** `gh workflow run nightly-promote.yml --repo nathant99/spark-anvil-site` → watch to `completed/success` → confirm `origin/main` advanced (git FF staging→main).
3. **🔴 WATCH THE CF BUILD LOGS for BOTH units** — `spark-anvil-site` (CORE) + `spark-anvil-play` (PLAY), via `scripts/watch_cf_build.py --worker <w> --logs <uuid>` (full uuid; per-worker tag). A build that logs **"Build output restored from build cache" + "Uploaded ~2 files"** and does NOT show the changed page rebuilding is a **STALE CACHE-RESTORE**, NOT a real rebuild — the source change did not reach the deployed artifact (R-SITE-INCREMENTAL-CACHE-HYGIENE). Confirm `check-site-internal-links [unit=…] OK` too.
4. **Flip the alias:** `gh workflow run promote-workers.yml` → `completed/success`. A CF build does NOT go live until this promotes the `alias=="main"` version. (The 3 steps — train → build → alias-flip — are ALL required; the alias-flip lags and is the step most often forgotten.)
5. **🔴 LIVE-VERIFY THE ACTUAL CONTENT, never the build/promote status** — grep the SERVED HTML/CSS for the change (e.g. the new class/marker, or that the content-hashed `play.<hash>.css` CHANGED and contains the new rule). A cache-restored build serves the OLD hash + old content even after a green build + promote-workers success — so "promoted + green" without a content-grep is a **false-SHIPPED** (§ R-AUTOMERGE-NOT-MERGED family). If STALE → **CACHE-BUST**: CF dashboard *Workers Builds → Clear build cache* (founder, R-CLOUDFLARE-SCOPED-DEPLOY) OR a config/dep bump (§ `spark-anvil-website.md` R-SITE-INCREMENTAL-CACHE-HYGIENE — wipes the incrementalBuild cache, own quiet-window PR), then re-promote + re-verify.
6. **FULL UI/UX testing** — automated capture sweep of the fixed surface(s) + any surface the fix touches, dual-scheme × desktop+mobile, console-error asserted, visually reviewed (the screenshot-DoD, `spark-anvil-website.md` § R-WEB-CLONE-SCREENSHOT-DOD). Only after the content-grep PASSES.

**INCIDENT (2026-08-23) that codified this:** the tutorforge dropzone (#2663) + cast-hero placeholders (#2661) were on `main` + promote-workers ran green, but the served `play.<hash>.css` was UNCHANGED and lacked `tf-dropzone` → the CF build had cache-restored stale output → the fixes were NOT live despite every green signal. Only the served-CSS grep caught it. Cross-refs: § R-CLOUDFLARE-WATCHED-MERGE-DEPLOY (the per-merge watch) · `spark-anvil-website.md` § R-SITE-INCREMENTAL-CACHE-HYGIENE / R-SITE-FAST-BUILD-DEV-SUBSET / R-SITE-CHAPTER-MANIFEST-SYNC GENERALIZE #1-3 · § R-AUTOMERGE-NOT-MERGED.

## 🔴 CRITICAL: After a prod deploy, run FULL UI/UX testing on the surfaces the LAST-24H COMMITS touched — commit-scoped, automated capture + VISUAL DoD, live prod; functional gates + curl-200 are NECESSARY-BUT-INSUFFICIENT, the VISUAL pixel review is MANDATORY and non-waivable (R-PROD-POST-DEPLOY-UIUX-SWEEP; founder-direct 2026-08-23, escalated CRITICAL 2026-08-25)

**🔴🔴 CRITICAL (founder-direct 2026-08-25, "make it critical"): a prod deploy is NOT "verified"/"shipped" — and MUST NOT be reported as such — until the surfaces its recent commits TOUCHED have had FULL UI/UX testing on LIVE prod, and that INCLUDES the VISUAL screenshot-DoD (render → capture → the agent READS the pixels), not just the functional gates. The load-bearing failure this escalation forbids: passing Vitest + Playwright e2e (renders / a11y-names / no-console-error, even light+dark) + a live `curl` (HTTP 200 + a content token) + a green `watch_cf_build.py --verify` (build-log gates + the live asset-RESOLUTION probe — assets EXIST/resolve, NOT that the page LOOKS right) is the FUNCTIONAL half — it is BLIND to "renders green but LOOKS wrong" (layout/hierarchy/prominence/contrast/clipping/reading-order/dark-safety, and the composite scroll-length/spacing shift from adding an element). Claiming a deploy "verified" on the functional gates ALONE — skipping the pixel review — is a CRITICAL DoD violation on the same footing as a dark route. (Codified after 2026-08-25: a prod deploy was reported "verified live" on green e2e + curl-200 WITHOUT the visual pass; the retroactive screenshot-DoD passed, but the skip was the defect.) This is the standing post-deploy sweep (composes § R-SITE-FORCE-PROMOTE-AND-VERIFY step 6 + prod-deploy DoD gate 3 + `spark-anvil-website.md` § R-WEB-CLONE-SCREENSHOT-DOD), COMMIT-SCOPED — you test what changed, not the whole fleet. Reusable one-command harness: `spark-anvil-site/scripts/uiux-prod-sweep.mjs "<route> …"` (node@22; captures each route light+dark × desktop+mobile to `/tmp/uiux-shots/`, asserts 200 + zero console/pageerror; the agent THEN Reads the shots). A UI-affecting change with NO recorded visual review is an incomplete, CRITICAL-gate-failing deploy:**
1. **Enumerate the touched surfaces** — `git log origin/main --since="24 hours ago" --no-merges --format="%s"` (skip `release:`/`chore(build)`/cache-bump), map each commit to its route(s) (a clone's `/play/<app>/*` sub-routes from the live landing nav; `/cast/<app>/*` readers; `/books`; marketing pages). One deploy wave is usually ONE app cluster (e.g. all-TutorForge).
2. **Automated capture gate** — headless-Chromium (node@22 + `@playwright/test`) against LIVE prod URLs (NO build needed — a throwaway `.mjs` placed in a site clone for node_modules resolution, run + rm; R-SITE-WORKTREE for any build). Capture EVERY touched route at **light + dark × desktop + mobile**, ASSERT HTTP 200 + **ZERO console/pageerror** per page. A non-200 or a console error is a defect.
3. **Visual DoD** — READ the screenshots; review the DELTA (surfaces the commits changed) closely + spot-check the rest for hierarchy/prominence/contrast/clipping/dark-safety/broken-media (the class the automated gate is BLIND to — e.g. the 2026-08-23 broken cast-opener box passed every gate + link-check but only the pixels caught it).
4. **Any defect → track + fix** via § R-SITE-FORCE-PROMOTE-AND-VERIFY (fix → staging → force-promote → cache-verify → re-test). Live-prod is ground truth: a curl-grep of a content-hashed asset can hit a stale CDN edge node → trust the RENDERED page (Playwright) for the visual verdict, and re-grep on a miss.

## Deploy STATUS is answered from the CLOUDFLARE BUILD LOGS of every affected unit, NOT from the green GitHub-Actions release-train run — the Actions run only proves the git FF + alias flip (R-DEPLOY-STATUS-FROM-CF-BUILD-LOGS; founder-direct 2026-08-23)

**A green `nightly-promote` / `promote-workers` GitHub-Actions run proves ONLY the git fast-forward (`staging`→`main`) + the Worker alias flip — NEVER that the actual Cloudflare Workers **Build** deployed real content. So "what's the deploy status?" (and any "is X deployed?") is answered ONLY after reading the CF Build log of EVERY affected unit (CORE `spark-anvil-site` + PLAY `spark-anvil-play`; the standalone Workers where touched) and asserting per unit, on the `build_trigger_metadata.branch == "main"` build: (1) `build_outcome == success`; (2) it ran **FULL** (`FULL_BUILD=1`) — a `main` build that ran `FAST_BUILD=1` is a defect (the FAST subset omits pages + no-ops the link-check; staging/preview correctly run FAST — check the BRANCH, not the timestamp); (3) the internal-link-check **RAN** (not `FAST_BUILD set … skipping`) + reported `OK`; (4) a SANE page count (CORE full ≈3400+, not the ~56-page subset); (5) not a stale cache-restore (`Restored from build cache` + `Uploaded ~2 files` with the changed page NOT rebuilt). Reporting "green/shipped" from the Actions run alone is a false-status on the § R-AUTOMERGE-NOT-MERGED footing. Guard (re-runnable, ~$0, exit 1 on FAIL): `source ~/.r2-env.sh && python3 scripts/watch_cf_build.py --verify`. GENERALIZES to every CF-built prod unit; composes ABOVE § R-SITE-FORCE-PROMOTE-AND-VERIFY (landing a fix) · § R-CLOUDFLARE-WATCHED-MERGE-DEPLOY (per-merge watch) · § R-PROD-MONITORING (liveness) · § R-BUILD-FAILURE-READ-FULL-LOG-FIRST.** Founder-flag 2026-08-23 (*"did you check cf build logs?"* → codify/guard/generalize/track).

**⚠ RELEASE-TRAIN DOUBLE-TRIGGER: a `terminated` build is a superseded duplicate, NEVER the deploy — and a terminated FULL `main` build leaves prod STALE even though git-`main` carries the commit (2026-08-27, Program #85 prod-verify).** One promote fires a `main` + `staging` CF build for the SAME commit ~1s apart; CF terminates one non-deterministically (R-SITE-BUILD-OUT-OF-ORDER). So (a) `watch_cf_build.py` now SKIPS terminated builds (never report `outcome=terminated` as "the prod build" — a false `--verify` FAIL on healthy prod), and (b) if the FULL `main` build TERMINATES, `promote-workers` gets no new `alias==main` version → **prod stays on the PREVIOUS deployment even though git-`main` already has the commit** → `git-main has X` + a green Actions promote ≠ X is LIVE. Confirm the DEPLOYED version's `created_on` is AFTER your merge + content-grep the served page; if the FULL build terminated, RE-TRIGGER the train (§ R-SITE-FORCE-PROMOTE-AND-VERIFY) — the nightly train won't reliably "just get it" (it terminated once). **⚠ DOUBLE-TRIGGER MAIN-BUILD-SKIP (`q-84f2b1`):** a same-SHA `staging` twin could de-dup the `main` build → no `alias=main` version → prod stale. Root-eliminated 2026-09-02 (preview trigger deleted); `--verify` still warns `MAIN-BUILD-SKIP suspected`. → `GUIDE_CLOUDFLARE_BUILD_MONITORING.md` § double-trigger hazards item 3.

**⚠ BUILT ≠ LIVE — a green FULL `main` build is NOT the LIVE deployment; the `promote-workers` alias-flip cron is GitHub-THROTTLED for hours and the asset-resolve probe PASSES on a stale prod (2026-08-28, prod ran ~9.75h stale with a GREEN `--verify`).** Deploy STATUS ALSO requires a **build-live convergence** check — the ACTIVE deployed worker version's `created_on` MUST be ≥ the newest successful `main` CF build (both units); `watch_cf_build.py --verify` now asserts it (horizon-gated `PENDING`/pass vs `✗ STALE`; env `BUILD_LIVE_HORIZON_MIN`, default 360). ## A CRITICAL-PATH release/deploy CI job MUST run on the SELF-HOSTED (Ubicloud) runner pool, NEVER `ubuntu-latest` — GitHub-hosted minutes exhaust mid-cycle and the job then dies at runner-init (≈2s, 0 steps, NO logs), silently blocking prod while the Ubicloud gates stay green; a 2s/no-log job failure is INFRA (runner-init), not script logic (R-RELEASE-TRAIN-UBICLOUD-RUNNERS; 2026-08-25)

**Every CRITICAL-PATH release/deploy job in a cost-constrained repo (the `spark-anvil-site` release train's `nightly-promote.yml` `promote` + `promote-workers.yml` `promote` — the git-FF-to-main + the CF alias-flip) MUST run on the SELF-HOSTED Ubicloud pool (`ubicloud-standard-2-arm`, the same pool the pre-flights use), NEVER `ubuntu-latest`. GitHub-HOSTED minutes / spending-limit exhaust part-way through a busy day, after which EVERY `ubuntu-latest` job fails at RUNNER-INIT — a ≈2-second, 0-step, NO-LOG `completed/failure` — while the Ubicloud jobs (pre-flight Vitest/build + scoped e2e) keep passing. The lethal shape: BOTH pre-flight gates GREEN, but `promote` fails → staging→main never FFs → NO prod deploy, with zero test signal and no logs to read. TWO load-bearing diagnostics, each a defect if ignored: (1) when "both gates green but prod didn't deploy," inspect the PROMOTE job's `runs-on` + timing — a 2s/0-step/no-log failure is INFRA (runner-init / minutes-exhausted / spending-limit), NOT a script bug (do NOT re-read logs that don't exist or re-run tests — R-BUILD-FAILURE-READ-FULL-LOG-FIRST's sibling: no-logs+2s = the runner never started); confirm the pattern by checking whether OTHER `ubuntu-latest` jobs (e.g. `promote-workers`) flipped from success→failure at the same wall-clock boundary while Ubicloud jobs stayed green. (2) the fix is to move the job to Ubicloud (aligns with the repo's standing Ubicloud cost-avoidance posture, § R-CI-SAFE-TO-SKIP), never to "wait for minutes to reset." GENERALIZES: any critical-path CI job whose failure blocks a deploy/merge, in ANY repo that meters GitHub-hosted minutes, is a latent silent-blocker on `ubuntu-latest` — put it on the self-hosted pool; a non-critical job (notify/skipped-by-default) MAY stay `ubuntu-latest`. Guard: `scripts/check_release_train_runners.py` (SHAPE-B WARN; reads the site workflows on `origin/staging` + flags any critical-path promote job on `ubuntu-latest`).** Incident → `REFERENCE_WORKFLOW.md` § R-RELEASE-TRAIN-UBICLOUD-RUNNERS. Composes with § R-DEPLOY-STATUS-FROM-CF-BUILD-LOGS (this is WHY a green Actions run ≠ a deploy) + § R-PROD-MONITORING (a `staging-drift-alarm` catches the downstream symptom).

**⚠ RUNNER-SIZE CALIBRATION (the complement to the runner-POOL rule above; 2026-09-23):** put the SLOWEST job on the BIGGEST Ubicloud runner, not the smallest — Ubicloud is ~pennies/run (`ubicloud-standard-2-arm` ≈ $0.00125/min, ~5× cheaper than GitHub) and consumes ZERO GitHub minutes (§ R-CI-GH-HOSTED-MINUTES-COST), so runner SIZE is a near-free latency lever. The 2026-09-23 audit found the release train's long-pole `preflight` job (39,840-test Vitest + the FULL CORE+PLAY build of ~4,243 routes, the ~25-35min bottleneck) on the SMALLEST `ubicloud-standard-2-arm` while the faster `preflight-e2e` ran on `ubicloud-standard-8-arm` — backwards; bumped `preflight` 2-arm → 4-arm (site #4102). But the win is SUBLINEAR, not ∝-cores: an Astro SSG build's page-render loop is largely SERIAL (`build.concurrency` WORSENS OOM) + memory-bound (`--max-old-space-size=6144`), so more cores mainly speeds the Vitest step (parallelizes well) + gives more RAM (less GC thrash) + the parallel Vite/esbuild bundling — expect ~1.3–1.8×, not 4×. Discipline: scale the slow job 2→4-arm, BENCHMARK 4 vs 8 before over-provisioning (bump to 8-arm to match e2e only if 4 isn't enough; don't go 16 — the serial render caps the return), and leave poll-bound jobs (`promote`/`promote-live` = git + CF-API waits) on 2-arm. Guarded by `check_release_train_runners.py` (the runner-map assertions). Evidence (deep-web-researched 2026-09-23): Ubicloud pricing/tiers (`ubicloud.com/docs/about/pricing`; standard discontinued for NEW accounts May 2026 → premium) + Astro `build.concurrency`/render-serialization (`withastro/astro#16782`, bitdoze Astro SSG build-speed).
## The GitHub Actions bill is dominated by HIGH-FREQUENCY `ubuntu-latest` SCHEDULED jobs — GitHub bills each job ROUNDED UP to a full minute and self-hosted/Ubicloud runners are FREE, so a hosted scheduled workflow's cost is ∝ its RUN-COUNT, not its duration; keep hosted crons ≤ hourly and offload frequent probing to a free independent prober (R-CI-GH-HOSTED-MINUTES-COST; 2026-08-25)

**GitHub Actions cost math has three load-bearing facts, and getting them wrong silently accretes a climbing bill: (1) SELF-HOSTED / Ubicloud runners consume ZERO GitHub minutes (GitHub bills ONLY hosted `ubuntu-*`/`macos-*`/`windows-*` jobs — `macos` at 10×, `ubuntu` 2-core ~$0.006/min in 2026); (2) GitHub rounds EACH JOB RUN UP to a full minute — a 30-second cron probe costs a WHOLE minute; (3) therefore a SCHEDULED hosted workflow's monthly cost is ∝ its RUN-COUNT, NOT its per-run duration. Disciplines, each a defect if violated: (a) heavy/long jobs run on Ubicloud (§ R-CI-SAFE-TO-SKIP / § R-RELEASE-TRAIN-UBICLOUD-RUNNERS); (b) a hosted SCHEDULED workflow's cron MINUTE field is a single fixed integer (fires ≤ once/hour) — NEVER `*`/`*/N`/a list (sub-hourly); (c) HIGH-FREQUENCY probing/monitoring is offloaded to a FREE independent prober (the Cloudflare `prod-monitor` Worker, cron `*/15`, ADR-174) and GitHub keeps ONLY a LOW-frequency independent crosscheck; (d) when the bill "keeps climbing," the driver is the hosted cron jobs — the personal-account billing API EXISTS but needs the `user` token scope (a bare 404 = missing scope; founder: `gh auth refresh -h github.com -s user` → `scripts/audit_ci_spend.py --billing`), else read **Billing → Usage** in the WEB UI (itemizes by workflow) + set an alert-only Actions **budget** (Billing → *Budgets and alerts*; `GUIDE_CI_SPEND_FOUNDER_STEPS_2026-10-01.md`). Guard: `scripts/check_gh_hosted_cron_cost.py` (SHAPE-B WARN; reads the site workflows on `origin/staging`; `--ci-mode` fails on a sub-hourly hosted scheduled cron OR — 2nd assertion — a `prod-monitor-crosscheck.yml` `watched=(...)` grace window smaller than `max(6× the watched monitor's cron cadence, 24h floor)`).** **⚠ CRON-CADENCE ↔ CROSSCHECK-GRACE COUPLING (2026-08-27):** slowing a monitor's cron obligates re-syncing its `prod-monitor-crosscheck.yml` grace (≥ max(6× cadence, 24h)) in the SAME change, and an event-driven (no-cron) monitor is a STATE-only entry — both enforced by the guard (2nd + 3rd assertions); incident detail → `REFERENCE_WORKFLOW.md` § R-CI-GH-HOSTED-MINUTES-COST. Composes with § R-CI-SAFE-TO-SKIP (the Ubicloud cost-avoidance posture) + § R-PROD-MONITORING / ADR-174 (the free CF Worker is the frequent prober; GitHub is the low-freq crosscheck).

## Actions ARTIFACT STORAGE is a separate, account-wide quota — a PR-frequency workflow must not store a heavy build artifact on its common path: build inline where one runner consumes it, and delete what must be passed between jobs once its consumers pass (R-CI-ARTIFACT-QUOTA; 2026-09-28)

**Artifact storage is billed and capped apart from runner minutes, and shared by every repo on the account. A per-PR 500–850 MB `e2e-dist` tar filled it (2026-09-28): every site PR's e2e gate went red at upload with no test signal. Two invariants: (1) when a single runner consumes the build (the scoped path, `scope.total == 1` — most PRs), build INLINE in that job and store nothing (Ubicloud minutes are ~free, R-CI-GH-HOSTED-MINUTES-COST); (2) an artifact that must pass between jobs (the 6-shard full sweep) is DELETED by a run-scoped job once its consumers pass. Guards: `scripts/check_ci_artifact_hygiene.py` (1) + `scripts/check_ci_artifact_cleanup.py` (2), both reading site origin/staging. Site #4191 + #4188; q-2983f3 / q-af3caa.**

## CI spend is WASTED RUNNER MINUTES, not storage — never pay for a run that can't produce a result; the PR Vitest gate runs the AFFECTED set (R-CI-SPEND-HYGIENE; 2026-09-28)

**Ubicloud bills runner MINUTES (PR gate × PR volume); the GitHub bill was artifact STORAGE, in GB-hours; expired artifacts bill until their RUNS are deleted. Hosted minutes are ONE account-wide quota. Six waste classes, each a defect: (1) no `timeout-minutes`, or a cap the work outgrew (KILL = paid, no result); (2) a PR-triggered paid workflow without concurrency `cancel-in-progress`, or a superseded run's heavy artifact; (3) a duplicate PR + post-merge-push trigger; (4) an always-red workflow; (5) the full suite on a one-clone PR → `scripts/ci-vitest-scope.sh` (FULL on shared diffs; never delete tests); (6) a scoped path that builds more than it tests; (7) scope drift: FULL triggers most PRs now hit (`audit_play_tests_paths.py`, H12). Guard `check_ci_spend_hygiene.py` (H7 ≥90% quota) + `REGISTRY_CI_SPEND.txt` + OVERVIEW #208.** Founder-direct 2026-09-28; `ADR-301`.

## Every PROD surface has automated black-box monitoring that is COMPLETE, CONTENT-asserting, and INDEPENDENT — and a self-guard keeps a surface (or a monitor) from being silently forgotten (R-PROD-MONITORING; 2026-08-21)

**Every PROD surface MUST have automated BLACK-BOX health monitoring that is COMPLETE, CONTENT-asserting, and INDEPENDENT (each a coverage defect on the R-ASSET-GEN-COMPLETENESS footing): probe every surface (site `.com`+`.org` · `/play` · CDN · Room `/api/room/*` · feedback-D1 · `/offline` · servers' `/version` · the monitors themselves) for the right status AND a known content token (FALSE-GREEN guard — a `200` can serve a broken page; reuse the § R-CLOUDFLARE-WATCHED-MERGE-DEPLOY grep oracle); enumerate each in `Docs/REGISTRY_PROD_MONITORING_COVERAGE.txt` with a monitor OR a `# MONITOR-EXCLUDED:` line; ensure WHO-WATCHES-THE-WATCHERS — the guard asserts each monitor workflow exists + is `schedule:`-cron'd (a GH-Actions/CF cron SILENTLY STOPS), plus runtime independence via ≥2 schedulers and/or a dead-man's-switch heartbeat. OWN-INFRA-first + no kid PII (infra monitoring is § R-SITE-SDK-POSTURE-permitted; any external SaaS heartbeat or push alerting channel is FOUNDER+ADR gated); ADVISORY-WARN + symptom-based (free-private repo = no hard block); never Ubicloud; ~$0. A prod surface with no monitor + no exclusion, a silently deleted/unscheduled monitor, or a status-only (false-green-blind) probe is a defect.
